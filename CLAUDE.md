# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Development
pnpm dev              # Start dev server
pnpm build            # Production build
pnpm generate         # Static generation
pnpm preview          # Preview production build

# Type checking
pnpm typecheck        # nuxt typecheck (uses project-local vue-tsc, not npx)

# Linting & formatting
pnpm lint:fix         # Run prettier:fix + eslint:fix
pnpm eslint           # Check ESLint
pnpm prettier         # Check Prettier

# Testing
pnpm test:unit        # Vitest (unit + nuxt environments, with coverage)
pnpm test:e2E         # Playwright e2e (Chromium, requires .env.test)

# Shopware API types
pnpm generate-types   # Regenerate api-types/storeApiTypes.d.ts from schema (then run pnpm lint:fix)
pnpm load-schema      # Reload Shopware API schema
```

### Package manager

pnpm 12 (pinned in `package.json`, CI and `node.dockerfile`). Settings live in `pnpm-workspace.yaml` (`.npmrc` is auth/registry only since pnpm 11). pnpm 12 rejects packages published less than 24 hours ago (`minimumReleaseAge`), also in an existing lockfile; update dependencies with pnpm 12 itself, not an older global pnpm (`docs/notes/2026-09-21-dependency-update.md`).

### Test-driven development

Work test-first (red, green, refactor): for a bug, first write a test that reproduces it and fails on the current code, then fix it; for new behaviour, write the tests that describe it before the implementation. The test lands in the same commit as the change it covers. Changes with nothing to assert (content, copy, styling, dependency bumps) skip this; say so in the commit message.

### Running a single test

```bash
# Vitest – filter by test name or file path
pnpm vitest run test/nuxt/useDeliveryTime.test.ts
pnpm vitest run --reporter=verbose -t "should return true"

# Playwright – filter by file
pnpm playwright test test/e2e/checkout.spec.ts
```

### Typecheck note

Always run `nuxt typecheck` via the `pnpm typecheck` script, not via `npx vue-tsc`. The global npx-cached `vue-tsc` version may not be compatible with the project's installed `vue-router`. If `.nuxt/tsconfig.json` has stale pnpm paths after a dependency update (or after adding/renaming a composable), run `pnpm nuxt prepare` to regenerate it.

`pnpm typecheck` must stay at zero errors; CI runs it in the lint job. The sources of `@shopware/composables` and the `@shopware/nuxt-module` plugin are part of the checked program, so two things keep them green (see `docs/notes/2026-09-08-issue-277-typecheck.md`):

- `shopware.d.ts` falls back to the api-client's default types for operations/schemas our instance does not expose, and keeps `LineItem.payload` optional.
- `api-gen.config.json` applies the upstream schema patches plus `api-types/storeApiSchema.shopbite.overrides.json` when generating types.

Until 1.5.2 a pnpm patch fixed the plugin's `ShopwareNuxtOptions` import (`./src`, not shipped). `@shopware/nuxt-module` 1.6 imports `ShopwareNuxtOptions` from its package name, so the patch is gone (`docs/notes/2026-11-18-dependency-update.md`). If a future version breaks the plugin's types again, patch it with `pnpm patch @shopware/nuxt-module@<version>` and add `patches/` to `node.dockerfile`'s `COPY`.

Do not name a project composable like one from the `@shopware/composables` layer (e.g. `useCategory`): the project version shadows the layer's inside the layer's own code as well.

## Architecture

### Backend-agnostic storefront (ADR 0001)

The storefront is moving to ports and adapters so it works against any shop backend; Shopware becomes one adapter. Read [`docs/adr/0001-backend-agnostic-storefront.md`](docs/adr/0001-backend-agnostic-storefront.md) (BFF, session, bounded contexts, migration steps 0–8) and use the words of [`GLOSSARY.md`](GLOSSARY.md) in code, tests and docs (dish, not product; cart line, not line item; path, not SEO URL).

- `shared/domain/<context>/` (`kernel`, `menu`, `ordering`, `customer`, `restaurant`, `discoverability`): domain types, value objects with validating constructors (`money`, `timeOfDay`, `calendarDate`, `timeZone`, `leadTime`, `wishedTime` with a service date, `openingInterval` up to 24:00, `holiday` as whole days, `dishConfiguration`), pure domain services (`earliestWishedTime`), `DomainError` codes. Times and dates are the restaurant's (`ShopConfig.timeZone`, runtime config `shopBite.timeZone`, default Europe/Berlin), never the server's or browser's clock. Pure TypeScript; the server imports it relatively, app code imports types only (see Layer imports).
- `server/ports/`: the nine port interfaces and `Backend`; visitor-specific ports take a `BackendSession`.
- `server/adapters/shopware/` (the only place that may import `#shopware`, `@shopware/*`, `api-types`) and `server/adapters/memory/` (demo restaurant in memory); `registry.ts` creates them, unimplemented ports reject with `not_implemented`. Server routes get the adapter set with `useBackend(event)` (`server/utils/backend.ts`, runtime config `shopBite.backend`: `shopware` default, `memory`); each adapter builds itself from the runtime config and answers frozen values. Caching and backoff stay in the routes, not in the adapters.
- `test/contract/`: one contract suite per port (`*.contract.ts`, scenario in domain terms) run against every adapter fixture by `runContract` (`*.spec.ts`, part of `pnpm test:unit`). A port method you implement gets its contract tests first, for both adapters. A port an adapter implements in part is `partlyImplemented()` (`server/adapters/notImplemented.ts`): the rest rejects with `not_implemented`.
- BFF routes answer domain types and map a `DomainError` to HTTP with `answerDomain()`/`toHttpError()` (`server/utils/domainHttp.ts`, one table `DOMAIN_ERROR_STATUS` for all routes; the answer carries `data.code`, never the backend's message).
- Moved in step 1 (restaurant operations): `GET /api/shop/config` (`ShopConfig`), `/api/shop/opening-hours` (`OpeningHours`), `/api/shop/holidays` (`Holiday[]`), `/api/shop/branches` (`Branch[]`) and `/api/checkout/shipping-methods` (`ShippingMethod[]`, `CheckoutPort.listShippingMethods`; Shopware: plugin `/shopbite/config` lead times plus Store API `/shipping-method` names, a method the plugin does not list is a delivery without lead time; memory: Lieferung 30, Abholung 15 minutes). Each is a cached function (`server/utils/shopData.ts`: `shop-config`, `shop-opening-hours`, `shop-holidays`, `shop-branches`, `shipping-methods`; `swr: false`, resilient loader) for server-side rendering and llms.txt; `?fresh=1` asks the port directly, never a cache or a last good answer, for the browser's live values and the checkout's gate; while the value's backoff is active (after an outage, cached or fresh) it fails fast without reaching the backend. Failures are DomainErrors, so cached and fresh answers carry `data.code` (`backend_unavailable` with 503). The Shopware adapter lets concurrent reads of the plugin's `/shopbite/config` share one request in flight (`sharingRequestsInFlight`, no caching). The browser calls no Store API for these areas.

- Moved in step 4 (session and cart): the storefront session and `CartPort` in both adapters. **Session** (`server/session/`, glue `server/utils/visitorSession.ts`, `server/plugins/visitor-session.ts`): an HttpOnly, SameSite=Lax cookie `shopbite-session` (`__Host-shopbite-session` and Secure when `public.storeUrl` is https) that carries each adapter's state (Shopware: the context token) sealed: AES-256-GCM, key by HKDF from `visitorSession.password` (`NUXT_VISITOR_SESSION_PASSWORD`, at least 32 characters; production does not start without it, development generates one; `previousPasswords` for a rotation: a cookie of a previous password is sealed again with the current one on its visit, drop the previous one only `maxAgeDays` later), format `v1.<key id>.<nonce>.<data>` (`seal.ts`). No server-side storage: sessions survive restarts and deploys. The payload has a session id and a version; every change of a state seals a new value, a cookie is only set when the request changed a state (or once a day to extend `maxAgeDays`, 30). A bounded registry per process (`createSessionRegistry`) keeps each session's newest version and serialises a visitor's writes, the cart's and the bridge's (`useVisitorSession(event).exclusive`; bridge reads run in parallel): a request with an older cookie is stale (`isStale()`), its writes are dropped, cart writes and bridge writes answer 409 `stale_session`, `useCartMutations` sends again after 150 ms, twice at most. Routes hand adapters `backendSession(event, backend.name, { create })` (with `forwardedFor`); cart reads never create a session. The old layer's `sw-context-token` cookie is taken over once (into the `shopware` state) and deleted. CSRF: SameSite=Lax plus `assertSameOriginWrite` (Origin must be the origin of `public.storeUrl`, the request's own or one of `visitorSession.allowedOrigins` (NUXT_VISITOR_SESSION_ALLOWED_ORIGINS, exact origins of any scheme, e.g. several https hosts behind a TLS-terminating proxy), scheme included, forwarded headers not trusted; else `Sec-Fetch-Site` same-origin; 403 `cross_site_request`; a write with neither header is no browser's and is accepted). Visitor-specific answers are `private, no-store` (`answerPrivately`). **Cart BFF**: `GET /api/cart`, `POST /api/cart/lines` (`{ dishId, variantId?, extraIds?, removedIngredientIds?, quantity }`), `PATCH`/`DELETE /api/cart/lines/[lineId]`, `POST /api/cart/vouchers` (`{ code }`), `DELETE /api/cart/vouchers/[code]`, all answering the domain `Cart` (`server/utils/cartRoutes.ts`). The Shopware adapter (`server/adapters/shopware/cart.ts`) keeps the line items of 2.6.1: a plain dish is a `product` line item (id = product id), a configured one the plugin's `container` with the same uuid5 id (`containerLineId()`: product id + sorted extra ids, plus `|without:` and the sorted, lower-cased removals), label and payload hints and children; names, number, parent and main ingredients come from one `/product` lookup (`sw-inheritance`) and the extras a dish offers from its `/cross-selling`, both kept 60 s in the adapter (bounded); a variant must belong to the dish, an extra be offered by it; a visitor without a token gets an empty cart without a request; every cart request (cart, product lookup, extras, currency) has a 10 s deadline (`requestTimeoutMs`), `storeApiGet`/`storeApiPost`/`storeApiForVisitor` and the bridge time out after 10 s, cart requests use the server's endpoint and carry `X-Forwarded-For` (`BackendSession.forwardedFor`); message texts and logged error causes carry no token; a write refused as `CHECKOUT__CART_LOCKED` is sent again once; cart errors become `CartMessage` codes. The memory adapter keeps carts per session in memory. **Transitional bridge** (steps 4 to 6, removed in step 7): the Shopware layer's browser client talks to `/api/store-api/**` (`server/api/store-api/[...path].ts`, `server/adapters/shopware/sessionBridge.ts`), which adds access key and context token from the session, forwards a header allowlist plus `X-Forwarded-For` as a proxy does (incoming chain plus socket address, `forwardedFor()`; Shopware honours it only when `TRUSTED_PROXIES` lists the storefront and the proxies in front of it, via `localhost` both `127.0.0.1` and `::1`); the proxy in front of the storefront must overwrite a client-sent `X-Forwarded-For` (nginx `proxy_set_header X-Forwarded-For $remote_addr`), otherwise a visitor forges addresses past Shopware's per-IP limits, refuses bodies over 1 MB before buffering, stores a token Shopware issues (login, logout, registration) and replaces the visitor's tokens in headers, every JSON string and key and text bodies (Shopware writes them into error texts), and the internal endpoint in routing errors; server-side rendering reads the token from the session (`app/plugins/store-api-session.ts` via `event.context.shopbiteStoreApiSession`, read only), and `app.vue` keeps the token out of the page payload. App: `useCartData()` (the `Cart` state, `refresh()` rejects on failure), `useCartMutations()` (`addLine`, `setQuantity`, `removeLine`; one queue, coalesced quantities), `useAddToCart` (`setSelectedDish(dish, dishId)`: the dish a variant belongs to), `useVoucherCode` (`appliedVouchers`, `removeVoucher`), `cartLineLabel()`/`cartLineHoldsDish()` in `app/utils/dish.ts`; `CartItem` takes `line`. Wishlist and contact moved behind the BFF in step 7 (below), which removed the bridge.

- Moved in step 5 (checkout and orders): `CheckoutPort` (but the shipping methods of step 1) and `OrderPort` in both adapters, contract suite `test/contract/ordering.contract.ts` (one backend: cart, checkout and orders together). **BFF** (`server/utils/checkoutRoutes.ts`: `answerVisitor` = private answer, CSRF and `exclusive` + 409 `stale_session` on writes, reads never create a session; body validation with field names in `data.details.field`): `GET`/`POST /api/checkout/selection` (`CheckoutSelection`: shipping and payment method of the next order, also with an empty cart; POST `{ shippingMethodId }` or `{ paymentMethodId }`, a method the cart cannot use is selected anyway and shows as a cart message), `GET /api/checkout/payment-methods` (`PaymentMethod[]`, the visitor's rules, `preferred` = the shop's default), `GET /api/checkout/orderer` (`{ orderer: Orderer | null }`, guest or logged-in customer with billing and delivery address), `POST /api/checkout/guest` (`GuestDetails`; names, street, city, e-mail required, phone 7–40 characters, company for a business, texts up to 255, postal code 50, no control characters), `PATCH /api/checkout/orderer/addresses/[addressId]`, `POST /api/checkout/orders` (`{ attemptId, wishedTime: { date, time }, note? }` → `PlacedOrder`: order, `redirectUrl`, `paymentFailed`), `GET /api/orders/[orderId]` (another visitor's order, a guessed id or number: 404) and `POST /api/orders/[orderId]/payment` (`{ paymentMethodId? }` → `{ redirectUrl }`, the payment retry). **Placing an order** (`server/utils/orderPlacement.ts`): the switch is read fresh (`shopConfigData.fresh()`), the wished time must lie in `wishedTimeWindow()` of the cart's shipping method (one grid step of grace for the browser's clock; 422 `outside_ordering_window`), then `placeOrder` and `startPayment`; a payment that cannot start still answers the order (`paymentFailed`, the checkout goes to `/bestellung/<id>/fehler`). At most once: the browser sends one `attemptId` per press of the order button and the same id only after `stale_session` (`usePlaceOrder`, no retry after a failure without answer); the process remembers placed attempts per session id and backend (bounded, 30 min) and answers them before the staleness check (a double click's second request; `answerVisitor`'s `known`). The order request waits up to 60 s (`ORDER_TIMEOUT_MS`); without an answer the session is marked unanswered (15 min, per process) and nothing is placed for it again: that request, a retry and a new press poll `listOrders(session, 1, 1)` for about 30 s for an order since the attempt and answer it, else 409 `order_status_unknown` (the checkout: "Wir konnten nicht feststellen, ob deine Bestellung eingegangen ist …"). A new attempt with an empty cart is 409 `order_already_placed` with `details.orderId` when the session placed an order in the last 15 minutes (another tab, a reload: the checkout says "Deine Bestellung ist bereits eingegangen." and links it, no payment, no tracking), else `cart_empty`. A reverse proxy needs a read timeout above about 110 s for `POST /api/checkout/orders` (nginx `proxy_read_timeout 120s`), otherwise the guest sees the generic failure text. **Writes in the browser**: one queue for every BFF write (`queuedWrite` in `app/utils/bffWrite.ts`: cart lines and vouchers, selection, guest, addresses, order, payment), a write waits for the answer (and cookie) of the one before; adding to the cart uses `keepalive`; `app.vue` starts a new visitor's session with `POST /api/session` (`server/api/session.post.ts`, a storefront-own state, no backend request) after the first page has loaded, when the server render found no session it can unseal (`event.context.shopbiteHasVisitorSession`, `app/plugins/visitor-has-session.server.ts`, `useState("visitor-has-session")`); the checkout reads the cart again after 1.5 and 3.5 s when it loads empty within 10 s of an add in the tab (`noteCartWrite`, `cartWrittenWithin`; a full navigation while the add lands). **Shopware adapter** (`server/adapters/shopware/ordering.ts`): the selection is the context's methods (`PATCH /context`, shop-wide `/context` without a token), guests are registered with the request of the 2.x form (`accountType`, the address fields as strings with `salutationId: ""`, `acceptedDataProtection`, `storefrontUrl` matched against the sales channel's domains like the layer did: `devStorefrontUrl`, else the request's origin; the domains are kept 10 min), an address without a country (`AddressInput.country: null`, what the checkout form sends) in the configured `public.site.countryId` as before, a country code by ISO code (`/country` filtered by `iso`, the Store API's limit is 100), a changed address keeps its salutation when the change names none, the order is `/checkout/order` with only `customerComment` (`orderComment()`: `Wunschlieferzeit: HH:MM` or `Wunschabholzeit: HH:MM`, a note on the next line; `readComment()` reads it back, a time well before the order is the next day), sent once with a 60 s deadline (timeout, lock, 5xx: `backend_unavailable`), refusals named by the cart's errors (`shopbite-ordering-*` → `ordering_closed`, blocked methods, unavailable dishes, else `validation_failed`; `CHECKOUT__CART_EMPTY` → `cart_empty`, 403 → `unauthenticated`), `/handle-payment`, `/order/payment`, orders from `/order` with the visitor's token (401/403 and other customers' orders are `not_found`), the payment methods without `preferred` when only the context cannot be read, states mapped to `OrderStatus`/`PaymentStatus`, promotions as discounts, `OrderLine.configuration` with removal ids from a product lookup; 10 s deadline per request, `X-Forwarded-For`, no token in errors. **Memory adapter** (`server/adapters/memory/ordering.ts`): selection, guest and orders per session token, orders from the memory cart (numbers from 10000), so menu → cart → checkout → confirmation runs with `NUXT_SHOP_BITE_BACKEND=memory` (no mails). **App**: `useCheckoutMethods()` (`selection`, `paymentMethods`, `selectShippingMethod`, `selectPaymentMethod`; one shared request for the selection), `useCheckoutOrderer()` (`registerGuest`, `updateAddress`; a guest's details set the customer state, so the header knows it), `usePlaceOrder()`, `useOrder(orderId)` (order pages, payment retry), `useDeliveryTime().wishedTimeFor()` (service date of a chosen time), `toGuestDetails()` in `useRegistrationForm` (a guest and, since step 6, an account go to the BFF), `Checkout/OrdererAddress` (the checkout's address edit, with the one `AddressForm` since step 6), `UserDetail` on the `Orderer`, `OrderConfirmation`/`OrderDetail` on the domain `Order` (`ORDER_STATUS_LABEL`, `PAYMENT_STATUS_LABEL` in `app/utils/orderStatus.ts`), `trackOrder(order)` one Matomo item per order line. Login and account registration in the checkout moved in step 6 (`Summary` reloads the orderer when `useCustomer().isLoggedIn` changes). **Bridge** narrowed to `BRIDGE_ROUTES` (`server/adapters/shopware/sessionBridge.ts`; account routes until step 6, see below); everything else 404 without a request (checkout, payment, cart writes, documents). `/api/payment-methods` (Restaurant schema) asks `CheckoutPort.listPaymentMethods()`.

- Moved in step 6 (customer account): `CustomerPort` in both adapters, contract suite `test/contract/customer.contract.ts` (one backend with cart, checkout and orders; fixtures expose the mails a backend sent). **BFF** (`server/api/account/**`, body checks in `server/utils/accountRoutes.ts`, all through `answerVisitor`: private, CSRF and `exclusive` + 409 `stale_session` on writes): `GET /api/account` (`{ customer: Customer | null }`, the logged-in customer, the session's guest or null), `POST /api/account/login` (`{ email, password }`), `/logout`, `/register` (`GuestDetails` + `password` → `{ customer, confirmationRequired }`), `/register/confirm` (the e-mail link's query parameters as they came), `/password-reset` (`{ email }`, 204 for an e-mail with and without account, also when Shopware's limit holds it back), `/password-reset/confirm` (`{ token, newPassword }`), `PATCH /api/account/profile` (`{ salutation?, firstName, lastName }`), `POST /api/account/email` (`{ email, password }`), `/password` (`{ currentPassword, newPassword }` → `{ loggedIn }`), `DELETE /api/account`, `GET`/`POST /api/account/addresses`, `PATCH`/`DELETE /api/account/addresses/[addressId]`, `POST /api/account/addresses/[addressId]/default` (`{ use: "billing" | "delivery" }`), `GET /api/account/orders?page=` (`OrderPort.listOrders`, 100 per page). New domain codes `account_not_confirmed` (403), `account_inactive` (403; Shopware 6.7 answers deactivated customers with bad credentials, the mapping of `CHECKOUT__CUSTOMER_IS_INACTIVE` is for other versions), `already_confirmed` (409), `rate_limited` (429, `details.retryAfterSeconds`), `address_in_use` (409). ### Shopware type system

Custom Shopware Store API types are auto-generated into `api-types/storeApiTypes.d.ts`. The module augmentation in `shopware.d.ts` wires them into the `#shopware` virtual module:

```ts
declare module "#shopware" {
  export type operations = import("./api-types/storeApiTypes").operations;
  export type Schemas =
    import("./api-types/storeApiTypes").components["schemas"];
}
```

Custom ShopBite plugin endpoints are prefixed `shopbite.*` in the operations type (e.g. `shopbite.business-hour.get`, `shopbite.config.get`). Run `pnpm generate-types` after Shopware plugin changes, then `pnpm lint:fix` (the generator output is not Prettier-formatted). `shopware.d.ts` merges the generated types with the api-client defaults so the composables layer typechecks (see Typecheck note).

### Composables layer

`@shopware/composables` is consumed as a **Nuxt layer** (via `extends` in `nuxt.config.ts`). This means its composables, components, and pages are auto-imported alongside the project's own `app/composables/`. Project-level composables override the layer.

Key custom composables:

- **Restaurant operations (ADR 0001 step 1)** – `useShopConfig()` (`acceptsOrders`, `timeZone`, `checkAcceptsOrders()`), `useOpeningHours()`, `useHolidays()`, `useShippingMethods()` (`deliveryTime`/`pickupTime` = lead time of the first delivery/pickup method or `null`, `leadTimeFor(methodId)`), `useServiceSchedule()` (time zone, hours and holidays, `null` until loaded) read the `/api/shop/*` and `/api/checkout/shipping-methods` routes through `loadShopData()` (`useShopData.ts`: cached on the server, `?fresh=1` with `withRetries` in the browser). They hold domain types (type imports from `shared/domain` only).
- **Restaurant time** – `app/utils/restaurantTime.ts` (pure, also used by llms.txt): everything is computed in the restaurant's time zone (`restaurantNow`), never the visitor's clock. `serviceSpans()` joins a late-night opening that the domain splits at midnight (Fri 17:00–24:00 + Sat 00:00–01:30 reads Fri 17:00–01:30; 00:00–24:00 days are not joined); `servicePeriodsOn()` adds yesterday's part after midnight (shown from 00:00 in the checkout's hint), like the plugin's ordering window (nothing on a holiday, not after a holiday). `storeStatusAt()` (store status pill, `useStoreStatus`), `wishedTimeWindow()` (checkout time choice), `firstSlot()`/`minutesInWindow()` for the 5-minute grid. Displays (`openingHours.ts`, `schema.ts`) use the joined spans; a span up to the end of the day reads `24:00` (schema.org `00:00`, a full day `00:00`–`23:59`).
- **`useDeliveryTime`** – the wished time window: today's spans only (yesterday's late-night span included), from now plus the lead time of the selected shipping method (`useShippingLeadTime`; 30 minutes while unknown) to the end of that span (a span up to 24:00 ends at the 23:55 slot, since 00:00 would read as this morning), never on a holiday; no pre-orders for a later day (the plugin refuses them). A window past midnight has min > max in the time input (reversed range); `validate()`, `slotFor()`, `firstSlotTime` work in the window's minutes.
- **Lead time per shipping method** (shopbite#6) – from the shop's shipping methods (`ShippingMethod.leadTime`); there is no global `deliveryTime` any more and no guessing from method names. `app/utils/leadTime.ts` (also used by llms.txt): `shippingLeadTime(methods, id)` for a method (unlisted = delivery without lead time), `fulfillmentLeadTime()` = first method of a fulfillment (`null` without one; home hero/facts and llms.txt then leave the time out), `FULFILLMENT_WORDING` (Wunschlieferzeit/Wunschabholzeit, Liefer-/Abholzeiten), `wishedTimeComment()`/`parseWishedTime()`. `useShippingLeadTime()` follows the checkout's selected shipping method (time field, hint, empty states, comment prefix). The order's `customerComment` is `Wunschlieferzeit: HH:MM` or `Wunschabholzeit: HH:MM`; readers accept both (older orders always say Wunschlieferzeit). The home facts have `kind: delivery` and `kind: pickup`
- **`useAddToCart`** – takes a dish or variant (`OrderableDish`, with the id of the dish a variant belongs to), `Extra`s and removed ingredient names (mapped to their ids from the dish's `ingredients`) and posts the configuration to `/api/cart/lines`; the Shopware adapter turns it into the 2.6.1 line items (plain `product`, or a `container` with the 2.6.1 uuid5 id, so configurations that differ only in removals stay two lines)
- **`useAddressAutocomplete`** – proxies Geoapify through `/api/address/autocomplete` to avoid exposing the API key client-side
- **`useShopConfig`** – the server renders from the cached `/api/shop/config` (60 s), the browser loads it live after hydration (`useLiveShopData`, together with hours, holidays and shipping methods) and the checkout every 10 s (`Checkout/Summary.vue`; the lead times only after hydration). The ShopBite plugin refuses an order while ordering is paused (`shopbite-ordering-paused`); as defence in depth and for a clear message, `checkAcceptsOrders()` asks `/api/shop/config?fresh=1` before an order and the checkout does not order when it is off or cannot be checked. Until the config is loaded the time zone is `shopBite.timeZone` (state `shop-time-zone`, from the server's runtime config)
- **`useWishlistEntries`** – the wishlist (#467, ADR 0001 step 7): an entry is a `WishlistEntry` (a `DishConfiguration` by ids, the menu number, `addedAt`). Customers keep entries in the backend through `/api/wishlist` (Shopware: the ShopBite plugin's `/shopbite/wishlist`, entity `shopbite_wishlist_item`, shopware-plugin#30), guests in localStorage `shopbite-wishlist` (`{ version: 2, entries, pending }`; the 2.x storage and the old `sw-wishlist-items` ids are converted once). `app.vue` loads it on mount and on login merges the guest entries into the account (logout reloads the guest's); a backend without a wishlist (501) keeps customers in localStorage. The customer's Shopware core wishlist moves into the plugin in the adapter's read. `WishlistSaveButton` (heart in the product sheet header, `aria-pressed` for the current configuration) gets the `WishlistSelection` from `ProductDetail` (`selection-changed`); `Wishlist.vue` adds rows with `useAddToCart` (same container line item as the sheet) and opens the sheet on the wishlist page with the saved configuration ("Anpassen").

### Product data model (what Shopware must contain)

The Shopware adapter reads plain Shopware entities with fixed names (`server/adapters/shopware/catalog.ts` maps them to the menu's domain types); seed data must match them exactly (`shopware/scripts/seed-demo-menu.py` is a working example):

- **Navigation:** menu sections are the children of the sales channel navigation root (`readNavigation main-navigation`), scoped to the menu root: `runtimeConfig.public.shopBite.menuCategoryId` if set, else `menuCategoryId` from `/store-api/shopbite/config` (plugin configuration per sales channel, #486). The Shopware adapter resolves it (`menuRootReader()`, `server/adapters/shopware/menuRoot.ts`, strict: it rejects when the plugin configuration cannot be read; the sitemap alone falls back to the navigation root); the BFF caches it as `menuRootData` (`server/utils/navigationData.ts`, cached function `menu-root`, `config` TTL, last good root during an outage), which `/api/menu/root` and the cached navigations `menu` and `home` use for key and tree (resolved once per request on `event.context` and passed to `getNavigation(kind, menuRootId)`, so key and tree never name two roots). In the app use `useMenuRootId()`, never read the env directly. Category icon comes from the custom field `shopbite_category_icon` (icones.js.org name such as `i-lucide-pizza`), set by the ShopBite plugin.
- **Property groups:** `Hauptzutaten` (ingredients on the card, deselectable on the detail page, removed ones are appended to the cart label with "-"), `Vegetarisch` and `Vegan` with the option `Ja` (diet badges), `Küche` (kitchen badge). Filterable groups appear as listing filters.
- **Extras:** product cross-sellings of type `productList`; the cross-selling name is the label ("Extras", "Beilagen"), the assigned products need a price and sales-channel visibility but no category. In the quick view each cross-selling is a collapsible checkbox list that shows 6 entries of a long list and a search field above 15 entries (`Product/CrossSelling.vue`). Selected extras become children of a `container` line item (`server/adapters/shopware/cart.ts`, handled by the ShopBite plugin). The bon card opens the quick view sheet (`Product/QuickView.vue`), whose state is the `produkt` query parameter (product number) via `useProductQuickView` (#325). That deep link is the product URL (#289, no product pages): `dishLink()` (`app/utils/productUrl.ts`) takes `Dish.path`, which the adapter sets from the product SEO URL when it carries `?produkt=` (the ShopBite plugin sets the template, shopware-plugin#28; the number must be `|url_encode|raw` in the template, the SEO escaper slugifies `ß`), and otherwise builds it from the section's path. The card name is a stretched link to it (a plain click stays in place); a number not in the list (a variant) is loaded (`/api/menu/dishes?number=`) and opens with its options selected. The quick view keeps its configuration in the URL (#411): `ohne` (deselected ingredients by name) and `extras` (extras by product number), written live with `router.replace` by `useQuickViewConfiguration`; a variant switch updates `produkt` without swapping the sheet's product (numbers the sheet switched to itself are pinned). The share button (`useShareLink`) uses the Web Share API, else copies the link.
- **Custom fields on products:** `shopbite_receipt_print_type` (`number` prints the menu number on the receipt, `label` prints the name) and `shopbite_delivery_time_factor` (int) and `shopbite_cart_upsell` (bool, suggests the product on the order confirmation step `/bestellung/bestaetigen` via `useCartUpsell`; variant parents are never suggested, a flag on a parent applies to its variants), all from the ShopBite plugin.
- **Allergens and additives (#485):** property groups `Allergene` and `Zusatzstoffe` from the ShopBite plugin (shopware-plugin#36, maintained in the backoffice), code in the option custom field `shopbite_code` (A-R, 1-12), product custom field `shopbite_allergens_checked` = lists complete. The adapter maps them to `Dish.foodLabels` (`checked` = `shopbite_allergens_checked`); `foodLabelText()` in `app/utils/dish.ts`. Shown only on request (#500): the bon card and the list show nothing, `Product/FoodLabels.vue` is an info button in the sheet's toolbar that opens a Reka popover (not teleported, so the dialog's focus trap holds) with the names written out; without `shopbite_allergens_checked` the sheet points to the restaurant's phone and never says "no allergens". **Includes filter `translated` too:** custom fields only come back when `customFields` is in the `product` and `property_group_option` includes (`DISH_CRITERIA` of the adapter, used by every catalog request).
- **Variants:** standard configurator settings (`Product/Configurator.vue`, the detail route's `configurator` as `variantGroups`); `/api/menu/dishes/[dishId]/variant` resolves a variant by option ids (`CatalogPort.findVariant`). ### Server routes

`server/api/address/autocomplete.get.ts` — Geoapify proxy (keeps API key server-side). Passes on only `text` (3–200 characters), `lang` (`/^[a-z]{2}$/`) and `limit` (1–10), 400 otherwise; the area filter comes from `public.shopBite.addressAutocomplete.boundingBox`, never from the query. Upstream errors are logged with the key redacted and answered with a generic 502 (ofetch messages contain the request URL). Identical lookups come from a bounded in-memory cache (5 min, 500 entries); lookups reaching Geoapify are rate limited per client IP (`addressAutocomplete.rateLimit`, token bucket in memory per process, capacity 0 = off; the IP comes from `X-Forwarded-For`, so the app must run behind a proxy that sets it). Helpers in `server/utils/addressAutocomplete.ts`.
`server/utils/shopware/adminApiClient.ts` — Admin API client for server-side Shopware operations requiring elevated credentials.
`server/api/__sitemap__/urls.get.ts` — dynamic `@nuxtjs/sitemap` source: the contact page and `NavigationPort.listSitemapEntries()` (Shopware: the pages of the main navigation and the menu root's tree, without links, folders and technical URLs) through `toSitemapUrls()`.
`server/routes/llms.txt.ts` — `/llms.txt` for AI assistants (#402): shop, hours, ordering and the menu with prices, ingredients and diets as Markdown, built by the pure `server/utils/llmsTxt.ts` (`toLlmsMenu()` from the catalog's sections and dishes); `swr` 1 h. Every source is optional (`Promise.allSettled`), content pages blocked in `robots.txt` are left out.
`server/utils/storeApi.ts` — `storeApiPost()`/`storeApiGet()` for the routes above and the Shopware adapter. Always send Store API criteria as a POST body (also via `apiClient.invoke("… post …", { body })`): as `_criteria` query parameters Shopware ignores the `includes` projection and returns every field (#312).
Pages without content throw `createNotFoundError()` (`app/utils/notFound.ts`): fatal only in the browser, because a fatal error makes Nitro log a `[request error] [fatal]` block per scanner request (#363).
`modules/dev-tooling.ts` registers `@nuxt/eslint`, `@nuxt/hints` and `@nuxt/test-utils/module` only when the storefront itself is the project (not for shops extending the layer, not inside `node_modules`); they are devDependencies, so never add them to `modules` in `nuxt.config.ts` (#378).
The cached handlers (`defineCachedEventHandler`, TTL `public.shopBite.cacheTtl`, a day for dishes (`product`), listings, sections (`category`)) can be emptied by the backoffice: `POST /api/_cache/purge` with `Authorization: Bearer $NUXT_CACHE_PURGE_SECRET` (route off without the secret, #484). `server/utils/cachePurge.ts` picks the Nitro keys (`cache:nitro:handlers:<name>:<escaped key>`) by id, so a new cached handler needs its `name` in `ALL` there and the id in its `getKey`. Menu handlers: `variant` (by dish id), and `menu-section`, `listing`, `search`, `top-sellers`, `upsell`, `dish`, `dish-number`, which every menu purge empties (a dish sheet carries its extras, which any product change can reach; a section's sub-sections group its parent's listing).
The Nitro cache is bounded (`server/plugins/bounded-cache.ts`): an LRU (`unstorage/drivers/lru-cache`) mounted at `cache:` with at most `cacheStorage.maxEntries` entries (5000) and `maxSizeMb` of serialised data (128), `NUXT_CACHE_STORAGE_*`; evicted entries are fetched again. A shop that mounts its own `nitro.storage.cache` keeps it, `maxEntries` 0 leaves the cache unbounded. The menu routes validate their parameters before they become keys (`server/utils/listingParams.ts`, 400 otherwise): section, dish and option ids as the backend's opaque ids (letters, digits, `-`, `_`, at most 64, lower-cased), `filters` as such ids (`|`-separated, at most 50, deduplicated and sorted), `number` at most 64 characters, `order` from `listingSortings` (empty = Shopware's standard sortings `name-asc`, `name-desc`, `price-asc`, `price-desc`, `topseller`, `score`; add custom sortings there), `p` 1–20, text queries at most 100 characters with whitespace collapsed.
Layout data is cached the same way, because every page renders it, a 404 too (once its own page and once `/__nuxt_error`): a vulnerability scanner probing 404 paths otherwise multiplied its request rate at Shopware many times over. With warm caches an SSR request asks Shopware only for the customer of a visitor with a session (`/account/customer`, step 6; the layer's `/context` read is gone since step 7); paths with non-ASCII characters that pass the known-path filter still make their lookups uncached, and the browser loads config, hours and holidays once per page load (below). Handlers and TTLs (`cacheTtl.*`, `NUXT_PUBLIC_SHOP_BITE_CACHE_TTL_*`): `/api/navigation/[kind]` (`main`, `footer`, `menu`, `home`; the key of `menu` and `home` includes the menu root; `navigation`, a day), `/api/breadcrumb/[sectionId]` (`category`; an unknown section is a 404 and not cached), `/api/top-sellers` (`listing`), `/api/payment-methods` (Restaurant schema, asked without a visitor context; `paymentMethods`, 1 h), the restaurant operations of `server/utils/shopData.ts` (cached functions `shop-config`, `shipping-methods`, `shop-branches`: `config`, 60 s; `shop-opening-hours`, `shop-holidays`: `businessHours`/`holidays`, 5 min), the menu root (cached function `menu-root`, `config`), `/api/resolve-path?path=` (`server/utils/pathRoutes.ts`: cached functions `path-route` and `known-paths`, `seoUrl`, 10 min; see SEO below). Config, hours, holidays, the menu root and the path caches use `swr: false`: with Nitro's default `swr: true` an expired entry is still served once, so the TTL would not cap the staleness. A failed Shopware request is never cached. During an outage the layout handlers, the restaurant operations and the menu root serve the last good answer per key and otherwise fail fast with 503; after a failure each handler asks Shopware again only after 30 s (`createResilientLoader`, `server/utils/backoff.ts`), and `storeApiGet`/`storeApiPost` do not retry (ofetch retries a GET once by default). Use the loader in a new cached handler; it answers a pause as the DomainError `backend_unavailable` (503 with `data.code` through `answerDomain`). A handler whose answer shape changes under its old name gets a versioned key (`versionedKey()`, `server/utils/cacheKeys.ts`, raise `ANSWER_SHAPE`), since shops may keep the cache in persistent storage. Before an order, `Checkout/Summary.vue` asks for the live switch (`checkAcceptsOrders`, `?fresh=1`) and does not order when it is off or cannot be checked. Only server-side rendering reads config, hours, holidays and shipping methods from the cache: `useAsyncData` reuses the server payload at hydration (a `refresh()` during hydration does not fetch either), so `useLiveShopData` (app.vue, error.vue) reloads the four keys live (`?fresh=1`) with `refreshNuxtData` after hydration; store status, wished time choice and order buttons then act on that. Keys contain no language or context: like all cached handlers they call Shopware with the sales channel's access key only. Every purge (any target) empties the layout handlers (`LAYOUT`), the lists and the cached functions of `LAYOUT_FUNCTIONS` (`path-route`, `known-paths`, `menu-root` and the restaurant operations); `{ "layout": true }` empties only the layout data (and `llms.txt`), for changes of hours, closing days or the checkout switch.

`server/plugins/security-headers.ts` sends the headers of `runtimeConfig.securityHeaders` (`NUXT_SECURITY_HEADERS_*`, empty value = header off, builders in `server/utils/securityHeaders.ts`) with every response: HSTS (only when `public.storeUrl` is https), `nosniff`, `X-Frame-Options: DENY` plus `Content-Security-Policy: frame-ancestors 'none'`, `Referrer-Policy`, `Permissions-Policy` (camera, microphone, geolocation, usb, browsing-topics off; Web Share and clipboard stay allowed). Rendered HTML gets `Cache-Control: private, no-store` (it may carry the visitor's cart or login, `useUserContextInSSR`) unless a route rule sets one, loses `x-powered-by`, and gets a `Content-Security-Policy-Report-Only` (self, Shopware endpoint, Matomo, extra hosts from `contentSecurityPolicyReportOnly.scriptSrc`/`connectSrc`/`imgSrc`, optional `reportUri`) whose `script-src` lists the sha256 of each inline script of that response (Nuxt's config script and the import map; JSON payload and JSON-LD are data blocks). Inline styles stay allowed (Vue style bindings). The service worker caches no pages (no `runtimeCaching`), so personalised HTML never lands in CacheStorage.
`modules/public-cache.ts` (local module, also active in shops extending the layer) adds a 30-day `Cache-Control` route rule for every file in the `public/` folders of all layers; Nitro serves them without one. `image.ipx.maxAge` gives resized logos the same lifetime. Replace a public file under a new name (#273).
`server/api/content/*.get.ts` — Nuxt Content queries for the pages. Do not call `queryCollection()` in page code: in the browser it downloads the SQLite WASM build (865 KB) on client-side navigation (#314).

### Client-side JavaScript budget (#314)

- Nothing that the first paint does not need belongs in the entry chunk. Components that only some shops use go behind `Lazy…` + `v-if` (`BranchSwitch`, the branches of `/api/shop/branches`); the Matomo registry is imported in `plugins/matomo.ts` after `onNuxtReady`, tracking pushes to `_paq` via `useTrackEvent`. Tracked URLs (`setCustomUrl`) go through `trackingUrl()` (`app/utils/trackingUrl.ts`): no fragment, and of the query only campaign parameters (`utm_*`, `mtm_*`, `pk_*`, `matomo_*`) and the quick view configuration (`produkt`, `ohne`, `extras`), because e-mail links carry one-time secrets; the password reset and registration confirmation pages also `router.replace` their query away once read.
- Overlays (`SbSheet`, collapsibles) are created on first use (`v-if` + `nextTick()` before opening), not mounted with the page — mounting forces a layout of the whole page.
- Long lists render on the server and hydrate on scroll: `hydrateWhenVisible(Component)` (`app/utils`) keeps the markup and the chunk, Used for the bon cards and the footer.
- `NuxtLink` prefetches on interaction only (`experimental.defaults.nuxtLink`), and Rolldown groups shared framework/UI modules into two chunks (`vite.build.rollupOptions.output.codeSplitting`). Measure with Lighthouse behind the h2 proxy (see `docs/notes/2026-09-10-issue-314-mobile-js-cost.md`) before changing either.

### Stylesheet (#319)

- Every family in the `--font-sans` stack costs a system font lookup per text style during the first layout. `fonts.defaults.fallbacks["sans-serif"]` is therefore limited to the phone system fonts (Roboto, Helvetica Neue); do not add desktop families back without measuring Style & Layout (`docs/notes/2026-09-12-issue-319-stylesheet-cost.md`).

### Style presets and base components (#439–#446)

### SEO

- This repository, deployed as the app, is the demo shop (demo.shopbite.de) and must not be crawled: its Dokploy deployment sets `NUXT_SITE_INDEXABLE=false`. Never set `site.indexable` in `nuxt.config.ts`: shops extending the layer would inherit it and drop out of search engines.
- `server/plugins/site-url.ts` makes `storeUrl` the nuxt-site-config URL, so canonical, sitemap and robots.txt share one base. Build absolute URLs with `toAbsoluteUrl(useSiteConfig().url, path)` (`app/utils/seo.ts`).
- `app.vue` sets the title template (`site.titleTemplate`), canonical from the route, `og:url`, fallback `og:image` (`site.ogImage`) and `twitter:card`. Page titles are plain (`"Warenkorb"`), never suffixed with the shop name. Indexable pages use `usePageSeo` (`standalone: true` skips the template, home page); menu sections use `useCategorySeo`, which overrides the canonical with the section's canonical path (`MenuSection.path`).
- Shopware's section paths end in `/` and redirect without it, but the sitemap module strips trailing slashes from every URL. Sitemap entries that need the slash carry `_trailingSlash: true` (`toSitemapUrls()`); `server/plugins/sitemap-trailing-slash.ts` restores it in the XML. Never normalise trailing slashes of the paths a backend answers.
- There are no section page routes: the catch-all `pages/[...all].vue` serves Markdown content pages first (never a backend matter) and otherwise the menu section of the path, whatever prefix the backend gives it (`/c/Pizza/`, `/speisekarte/pizza/`); paths with a file extension 404 without a backend request. `useSectionRoute()` asks `/api/resolve-path` (`NavigationPort.resolvePath`): null is a 404, a redirect a 301 to the canonical path with the query kept (dish links `?produkt=`). The Shopware adapter finds category SEO URLs only (product SEO URLs have no page, #289) and redirects other spellings: other casing, toggled trailing slash, technical URLs (`/navigation/<id>` by `pathInfo`), and old SEO URLs that Shopware keeps after a template or name change (`isCanonical: null`; the Store API hides them unless the criteria filter on `isCanonical`, so they are looked up last, with and without the slash, then the canonical one of the same category and language). `server/utils/pathRoutes.ts` shields the backend: paths no section can have are answered null without any request (`isHostilePath` in `shared/domain/discoverability/paths.ts`: undecodable or invalid UTF-8, `%25`, `..`, control characters, a leading `//` or `/\` (also encoded), longer than 750; the Shopware adapter adds technical prefixes not followed by a 32-hex id, `isHostileShopwarePath`); then the path is checked against all current and former section paths (`NavigationPort.listKnownPaths`, cached as `known-paths`, `cacheTtl.seoUrl`; Shopware pages its category SEO URLs with `page`, which `/seo-url` honours, not `p`, sorted by `id`), compared as `pathKey()` (decoded with `decodeURIComponent`, lower case, without accents, `ß`/`æ`/`œ` written out, without outer slashes; a key with non-ASCII characters or `%` is always let through, since MySQL's collation may match it; paths under `KnownPaths.unlistedPrefixes`, Shopware's technical URLs, too), so a path no section ever had is a 404 without four lookups. Lookups are cached as `path-route` by the path in lower case (unlisted prefixes are case-sensitive and keyed apart, so `/Navigation/<id>` is not the technical `/navigation/<id>`): one entry serves every casing, the answer for the visited spelling is rebuilt with `routeTo()`. Only paths that spell the canonical path up to case (also with the slash toggled) and unlisted ones (one per entity) are stored; misses, former paths and loose matches of the collation (accents, trailing spaces) never create an entry, so a scanner cannot grow the cache per spelling. Operator caveat: a section created or renamed in the Shopware Administration without a purge 404s at its new URL until the list expires (`cacheTtl.seoUrl`, 10 min); the backoffice purge or any `POST /api/_cache/purge` fixes it at once, `NUXT_PUBLIC_SHOP_BITE_CACHE_TTL_SEO_URL` shortens the window. More than 1000 entries per kind is cached as "no filtering"; a failed load lets every path through for 30 s without asking again; during an outage of the lookups the route fails fast with 503 after the first failure.
- `@nuxtjs/sitemap` must stay before `@nuxt/content` in `modules`; content collections need the `sitemap` schema field to appear in the sitemap.
- The home page FAQ (`faq` in `content/index.yml`, `Home/Faq.vue`, #404) uses native `<details>`, not a Reka accordion, which unmounts closed panels, and the answers must be in the SSR HTML. The same items feed the `FAQPage` JSON-LD and `/llms.txt`.
- `server/plugins/ai-crawlers.ts` adds two named robots.txt groups via the `robots:config` hook (#403): AI search/assistant bots and AI training bots (lists with sources in `server/utils/aiCrawlers.ts`), toggled by `runtimeConfig.aiCrawlers.search`/`.training`. A crawler matching a named group ignores `*`, so allowed groups repeat the `robots.disallow` paths.
- Shop contact data (NAP) lives in `runtimeConfig.public.site` (`address.*`, `telephone`, `googleBusinessProfileUrl`; `alternateNames` lists other names the shop is listed under, for the Restaurant schema `alternateName` and `/llms.txt`) and is rendered by `components/Footer/Contact.vue`. `useOpeningHours`/`useHolidays` use `immediate: false` (during SSR they read the cached `/api/shop/*` routes, after hydration `useLiveShopData` loads them live); a component that needs them in the SSR HTML calls `onServerPrefetch(() => refresh())`. In the browser both requests are retried twice (`withRetries`); `useOpeningHoursData` gives components the combined loading/failed state and `retry()`, and reports a failure only after mounting (a failed server prefetch would otherwise break hydration, #355). Anything that depends on the current time (open/closed status, "today") is computed after mounting: `useStoreStatus` starts its clock in `onMounted`, because the home page prefetches the hours on the server and the status may change between the server render and hydration (#365). The time zone is the restaurant's (`ShopConfig.timeZone`), not the visitor's.

### Layer imports

Shops extend the storefront as a Nuxt layer, so paths must resolve from the storefront itself: `~`, `@` and `#shared` point to the shop's folders there. App code imports nothing from `shared/` but types (`import type … from "../../shared/domain"`, erased at build; a value import broke the Nitro server bundle in 2.0.1; app-local helpers such as `restaurantTime.ts` instead), so `modules/theme.ts` passes what the app needs through runtime config (`shopBite.themePresets`). Files in `nuxt.config.ts` use `fileURLToPath(new URL("./…", import.meta.url))` (`css`, local modules). `main.css` lists `@source "../.."`, because Tailwind's automatic detection only scans the shop. `test/layer/` is a minimal shop (`extends: ["../.."]`) that the CI job `layer-build` builds (`pnpm nuxt build test/layer`); 2.0.0 broke every shop because only the storefront itself was built.

### Testing setup

Two Vitest projects in `vitest.config.ts`:

- **`unit`** – `test/unit/**` and `test/contract/**`, Node environment, pure function, domain, adapter and contract tests
- **`nuxt`** – `test/nuxt/`, Nuxt environment via `@nuxt/test-utils`, for composables and components

In `test/nuxt/`, a `mockNuxtImport("useRuntimeConfig")` without `app.baseURL` breaks the router setup of the test environment (`useRouter()` is undefined, see `useAddressAutocomplete.test.ts` for a working mock). For config values, prefer setting them on the real config, e.g. `Object.assign(useRuntimeConfig().public.site, { … })`.

Accessibility checks (#446) in `test/a11y/` run axe (WCAG 2.1 AA) on home, menu, product sheet, cart, checkout, order confirmation and payment failure (the order is a mocked answer of `/api/orders/[orderId]`), login, registration and the password pages, search, contact, wishlist, a content page and the 404 page, desktop and phone (`pnpm test:a11y`, Playwright projects `a11y` and `a11y-mobile`); serious and critical violations fail. They need no login and only add a product to a guest cart. They test the running build (Playwright starts `.output/server/index.mjs`); the preset is runtime config, so CI runs the `a11y` matrix job per preset on one build with `NUXT_PUBLIC_SHOP_BITE_THEME_PRESET`. Locally: `pnpm build`, then `NUXT_PUBLIC_SHOP_BITE_THEME_PRESET=grill NUXT_PUBLIC_STORE_URL=http://localhost:<port> pnpm test:a11y`.

E2E tests in `test/e2e/` use Playwright (Chromium only) and require `TEST_USER` / `TEST_USER_PASS` env vars. A local dev server must be running before the suite executes.
