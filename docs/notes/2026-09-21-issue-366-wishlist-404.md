# Issue #366: wishlist 404 logged as an error

## Finding

`useSyncWishlist` of `@shopware/composables` (1.12.1) catches every error of
`readCustomerWishlist post /customer/wishlist` and logs it with
`console.error`. Two responses are expected states, not errors:

| Response | Code                                  | When                                         |
| -------- | ------------------------------------- | -------------------------------------------- |
| 404      | `CHECKOUT__WISHLIST_NOT_FOUND`        | logged-in customer who never saved a product |
| 403      | `CHECKOUT__WISHLIST_IS_NOT_ACTIVATED` | wishlist disabled in Shopware (demo shop)    |

The log happens inside the layer, so a `try/catch` around
`getWishlistProducts()` in `app.vue` cannot suppress it. The layer's
`useWishlist` also calls it after login (`mergeWishlistProducts`).

The guard in `app.vue` checked the route name for `wishlist`, but the page is
`merkliste`, so `/merkliste` fetched the wishlist twice (`app.vue` and
`components/Wishlist.vue`).

## Fix

- `app/composables/useSyncWishlist.ts` overrides the layer composable (a
  project composable with the same name also replaces it inside the layer's
  `useWishlist`). It is a copy of 1.12.1 that skips the log for the two codes
  above. Compare with the layer source when Renovate bumps
  `@shopware/composables`.
- `app.vue` compares the route name with `merkliste`.

## Verification (2026-09-21)

Dev server against `shopware.shopbite.de` with a logged-in test customer: one
wishlist request on `/` and one on `/merkliste`, no
`[useSyncWishlist][getWishlistProducts][error]` in the console. The browser
still prints its own "Failed to load resource" line for the 403/404 response;
that is not a JavaScript error and cannot be suppressed from the page.

`storefront/.env` currently points at the La Fattoria production backend; to test
against the demo, set `NUXT_PUBLIC_SHOPWARE_ENDPOINT`/`_ACCESS_TOKEN` in the
environment (they take precedence over `.env`).
