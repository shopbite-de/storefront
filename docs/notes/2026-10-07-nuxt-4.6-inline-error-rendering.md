# Nuxt 4.6 `experimental.inlineErrorRendering`: no gain, not enabled

As of 2026-10-07, after the update to Nuxt 4.6.0 (#424). Measured on a throwaway branch, not merged.

## What the option does

With `experimental.inlineErrorRendering: true` (default from `compatibilityVersion: 5`), a failed server render shows `error.vue` in the same request. Without it, Nuxt passes the error to Nitro, which renders the error page through an internal request to `/__nuxt_error`. The hope was cheaper 404s for scanner traffic (#363).

## Measurement

Two production builds (with and without the flag) against the demo backend (`shopware.shopbite.de`), 400 requests per run with 4 parallel, server CPU time read from `/proc/<pid>/stat`:

| | without | with |
| --- | --- | --- |
| `/wp-login.php`, 4 runs | 48 ms CPU/request | 59 ms |
| `/gibtsnicht` (unknown category), 3 runs | 52 ms | 54 ms |
| `/impressum` (control, flag has no effect) | 42 ms | 52 ms |

The runs scatter by 10–25 ms, and the control page differs by 10 ms although the flag does not touch it. No saving is visible. Response times are dominated by the Store API requests and say nothing either way.

## Side effects on 404 responses

- `cache-control: no-cache` and `vary: accept, sec-fetch-mode` are missing (they come from Nuxt's Nitro error handler). Without `cache-control`, proxies and CDNs may cache a 404 heuristically.
- The 404 page gets an extra `<meta name="robots" content="index, follow, …">`.
- Every 404 still logs an error object to the server log, only in a different format. The flag does not fix #363.

Status codes, page titles and regular pages are unchanged.

## Decision

Not enabled. Check again when moving to `compatibilityVersion: 5` or Nuxt 5, where it becomes the default: in particular whether 404 responses then carry a `cache-control` header again.
