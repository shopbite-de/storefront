# Issue #294: Matomo without configuration loads `cdn.matomo.cloud/undefined`

As of 2026-09-10, branch `fix/294-matomo-without-config`.

## Cause

- `$production.scripts.registry.matomoAnalytics: { trigger: "onNuxtReady" }` made the plugin generated by `@nuxt/scripts` call `useScriptMatomoAnalytics()` on every page, regardless of the configuration.
- The registry implementation (`runtime/registry/matomo-analytics.js`, 1.3.9) falls back to the Matomo cloud without `matomoUrl`: `https://cdn.matomo.cloud/${cloudId}/`. Without `cloudId` that becomes `.../undefined/matomo.js`.
- `useTrackEvent` also called `useScriptMatomoAnalytics()` unconditionally. In the dev server (no registry entry there) that loaded the script on the first tracking call with the default trigger `client`.
- Result without Matomo env (demo shops, new customers): a 404 in the console and a request carrying the visitor's IP to a third party without consent.

## Solution

- Registry entry removed. `app/composables/useMatomo.ts` only creates the script when `matomoUrl` and `siteId` are set in `runtimeConfig.public.scripts.matomoAnalytics`, otherwise `null`.
- `app/plugins/matomo.ts` (universal, so the preload stays in the SSR HTML) calls `useMatomo()` on every page; it replaces the generated registry plugin incl. page view tracking.
- `useTrackEvent` pushes through `useMatomo()?.proxy._paq`; without configuration tracking is a no-op.
- No option values are passed: `useRegistryScript` merges `runtimeConfig.public.scripts.matomoAnalytics` itself via `defu`. Plugin and `useTrackEvent` therefore get the same script instance (same key, same `src`). The rule from #259 still holds: no placeholder values in options that get inlined into the build.

## Pitfalls

- The build warning `env var NUXT_PUBLIC_SCRIPTS_MATOMO_ANALYTICS_MATOMO_URL is set but matomoAnalytics is not registered in scripts.registry` is a false positive: the `@nuxt/scripts` validator only checks the registry entry. The values still arrive via `runtimeConfig.public.scripts.matomoAnalytics` (see verification).
- A `mockNuxtImport("useRuntimeConfig")` without `app.baseURL` breaks the router setup of the Nuxt test environment (`useRouter()` in `@nuxt/test-utils` is then `undefined`; `HeaderRight.test.ts` mocks with `app.baseURL` and works). `test/nuxt/useTrackEvent.test.ts` therefore sets the real runtime config.

## Verification

Production build locally against the La Fattoria Store API, three scenarios, Playwright records every request containing `matomo`:

- Without Matomo env and with `MATOMO_URL` only: no `matomo.js` reference in the SSR HTML, no request (neither `cdn.matomo.cloud` nor anything else).
- With URL + site ID: preload and request to `<matomoUrl>/matomo.js`, `_paq` contains `setTrackerUrl`, `setSiteId`, `trackPageView`. A client-side search from `/c/Pizza/` to `/suche?q=salat` pushes `trackSiteSearch` through the same instance (only one script request).

## Behaviour change

Matomo now depends only on the configuration, no longer on `$production`. A dev server with a complete Matomo env therefore loads Matomo from the first page view (previously only on the first tracking event).
